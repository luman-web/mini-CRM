# Мини-CRM «Объекты и задачи»

Тестовое приложение для строительной компании: постановщики создают задачи по объектам, исполнители выполняют их и отправляют на проверку.

## Стек

- React 18 + TypeScript + Vite;
- Ant Design;
- Supabase Auth и PostgreSQL;
- RLS, триггеры и защищённые RPC-функции для контроля доступа.

## Локальный запуск

Требуется Node.js 24 или новее. Если используется `nvm`:

```bash
nvm use
npm install
cp .env.example .env
npm run dev
```

В `.env` укажите URL проекта Supabase и publishable key. `service_role` и secret key во фронтенде не используются.

## Настройка Supabase

1. Создайте проект Supabase.
2. Примените миграцию из `supabase/migrations` через Supabase CLI или SQL Editor.
3. В настройках Auth отключите открытую регистрацию (`Allow new users to sign up`).
4. Создайте минимум трёх пользователей вручную: одного постановщика и двух исполнителей.
5. Добавьте для каждого пользователя строку в `public.profiles`, используя UUID из Auth:

```sql
insert into public.profiles (id, full_name, role) values
  ('UUID_ПОСТАНОВЩИКА', 'Анна Руководитель', 'setter'),
  ('UUID_ИСПОЛНИТЕЛЯ_1', 'Иван Исполнитель', 'executor'),
  ('UUID_ИСПОЛНИТЕЛЯ_2', 'Мария Исполнитель', 'executor');
```

## Правила предметной области

- Постановщик видит всё; исполнитель — только назначенные ему задачи и связанные объекты.
- Принять задачу или вернуть её на доработку может только её автор.
- Исполнитель меняет статус только в разрешённой последовательности.
- Комментарий при возврате на доработку обязателен.
- Редактировать поля можно только у активной задачи в статусе `new`; каждое изменение автоматически записывается в историю.
- После начала работы назначенного исполнителя менять нельзя.
- Начатую задачу можно архивировать и восстановить без потери истории.
- Физически удалить можно только активную неназначенную задачу в статусе `new`.
- Объект можно удалить только тогда, когда у него нет задач.
- Уведомления создаются из событий истории: постановщик узнаёт об отправке на проверку, исполнитель — о назначении, доработке, принятии, архивировании и восстановлении задачи.

## Защита данных

- RLS ограничивает чтение и запись на уровне PostgreSQL, поэтому скрытие кнопок в интерфейсе не является единственной защитой.
- Статус нельзя изменить обычным `UPDATE`: клиент вызывает `transition_task`, а база проверяет пользователя и допустимость перехода.
- Архивирование и восстановление выполняются функциями `archive_task` и `restore_task`.
- `task_events` доступна клиентам только для чтения. События создают триггеры и защищённые функции.
- `notifications` защищена RLS: пользователь читает только свои уведомления и может изменить у них только отметку о прочтении.
- Секретные ключи не нужны браузерному приложению и не должны попадать в репозиторий.

## Принятые допущения

- Архив — отдельный признак задачи, а не дополнительный статус рабочего процесса.
- Создание задачи — первое событие истории (`— → Новая`).
- Изменение нескольких полей одним запросом сохраняется одним событием с перечнем старых и новых значений.
- Удаление новой неназначенной задачи удаляет и её первоначальную историю. Это единственное контролируемое исключение из бессрочного хранения истории.
- Пустой объект можно удалить; объект с задачами база удалить не позволит.
